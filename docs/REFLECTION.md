# One-page reflection

**With 3 months instead of 8 hours.** I would build the rest of the pipeline in the order of risk: (1) the mapper with a stored, versioned mapping table and a review UI; (2) FX translation and the cumulative translation adjustment, which I deliberately did not attempt; (3) the four statements with the identity checks (A = L + E, net income ties between P&L and SOCIE, closing cash ties to the balance sheet); (4) a persistence layer with the lineage table so any statement cell drills to source rows; (5) a golden set of ugly real-world files as regression tests, with the model and prompt version pinned. I would also talk to an accountant and a real auditor early, because several of my rules are guesses about what finance teams treat as suspicious.

**Where the prototype breaks at scale.** It loads everything in memory with plain Python. It matches accounts by exact code, so it will not cope with ERP-specific codes without the mapper. The duplicate-depreciation and FX-reval rules are hand-written for these patterns; at thousands of accounts and many entry types I would need a rule library with configuration per client, not code per rule. Multi-entity consolidation (entity IDs, intercompany matching across entities, per-entity FX) is absent, and the suggestion ranking is a simple text-plus-code-proximity score that I would replace with learned mappings from approved history. Rule thresholds such as the 1% tolerance and the 500k review limit are placeholders that should come from the client.

**How I used AI tools.** I used Claude as a learning partner and a speed-up, not as a replacement for my own thinking. As an intern, I’m new to financial reporting, so I used it to understand the accounting concepts behind the data (trial balances, accruals, FX revaluation, intercompany entries) and to find problems in the mock files. It also helped me draft the architecture and write the code and tests.

I tried not to take its answers on trust. I ran the code on the original files without changing them, recomputed key numbers myself, and asked Claude to check its own work against the assignment. That found mistakes I would have missed, such as an inconsistent example and some claims in my document that went further than what the prototype actually does. I corrected them.

It was least reliable on accounting policy, such as whether the numbers are year-to-date or quarterly, so I wrote those down as assumptions and questions for a finance expert instead of guessing. The biggest thing I learned is to use AI to move faster while still verifying the results.

**What I think is being underestimated.** The definition of "correct" is not arithmetic; it is agreed meaning. Whether the TB is quarter or year-to-date, whether amounts are translated, whether the prior period is pre- or post-close, and how retained earnings and the translation reserve roll forward all change every statement, and none of it is in the files. A system that quietly picks an interpretation will produce statements that tie perfectly and are still wrong. The most valuable feature is therefore not generation but making these assumptions explicit, recorded and signed off, with every output labelled provisional until they are.
